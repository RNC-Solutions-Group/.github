# Contributing to RNC Solutions Group projects

Thank you for taking the time to improve a project. These are organization-wide defaults; each repository's own README, contribution guidelines, security policy, and license take precedence.

## Before you start

1. Read the project's README and available documentation.
2. Search existing issues and pull requests to avoid duplicate work.
3. For substantial changes, open an issue first to confirm the problem, scope, and expected outcome.
4. Follow the repository's setup and verification instructions. Do not assume all RNC projects use the same stack.

## Issues

Use **Bug report** for unexpected behavior, **Feature request** for improvements, and **Development task** for scoped implementation or maintenance work. Include enough context for someone else to understand the request and confirm completion.

Do not post credentials, private client information, or sensitive logs. Report security vulnerabilities privately to the project maintainers; use GitHub's private vulnerability reporting where the repository offers it.

## Pull requests

1. Create a short-lived feature or fix branch; do not commit directly to `main`.
2. Keep the change focused and link the issue or decision that motivated it.
3. Include tests and documentation appropriate to the change, or explain why they are not applicable.
4. Run the repository's available checks and record results in the pull request.
5. Call out security implications, breaking changes, migrations, and deployment/rollback needs.
6. Submit a pull request for review. Repository maintainers handle approval and merge.

Avoid unrelated refactoring in the same pull request. Never commit passwords, API tokens, real customer records, or environment files containing secrets.

## Licensing and reuse

Projects can have different distribution and licensing models. Check the specific repository's license before using, modifying, or redistributing its content. The presence of source code or an issue template does **not** grant open-source permissions.

## Community standards

Be clear, constructive, and respectful. Prefer technical evidence, reproducible reports, and specific recommendations over assumptions. The goal is useful work that another contributor can understand and maintain.
